Scalable Merchant Payment Processing Platform
 
⭐ Featured

A Razorpay-inspired payment gateway built from scratch in Java Spring Boot. Covers the complete lifecycle — merchant onboarding, API key management, order creation, payment initiation, authorization, capture, and card tokenization — with production-grade security and domain-driven architecture.

→Payment State Machine — 14 transitions (CREATED→AUTHORIZING→AUTHORIZED→CAPTURING→CAPTURED→SETTLED/REFUNDED), immutable audit log per transition
→AES-256-GCM envelope encryption — per-card DEK encrypted by master key, raw PAN zero-filled from JVM heap after use (PCI-DSS Req 3.5)
→Dual auth — JWT Bearer (merchant routes) + API Key Basic Auth with BCrypt + 24hr key rotation grace period (previousKeySecretHash)
→Strategy + Adapter pattern — pluggable payment methods (Card via Vault, UPI, NetBanking), zero core changes to add new methods
→Bank Callback Simulator — ChaosMode (SUCCESS/FAILURE/TIMEOUT/SLOW/NORMAL), per-method success rates, deterministic via hashCode bucketing
→MerchantContext @RequestScope — merchant identity from filter chain, AuditorAware for JPA audit trail (keyId → merchantId → SYSTEM)
// design decision — why a state machine, not a status enum
ProblemA payment moves through real, irreversible stages (authorize → capture → settle). A plain status field lets any code path jump straight from CREATED to SETTLED, or double-capture the same payment — both are real money bugs, not edge cases.
DecisionModeled payment status as an explicit 14-transition state machine, where every transition is validated against a fixed transition table and recorded in an immutable PaymentTransitionLog. Invalid transitions throw InvalidStateTransitionException before any DB write happens.
Trade-offMore upfront design and boilerplate (transition table, guard checks, one exception per illegal edge) vs. a one-line status = "CAPTURED". Chose correctness over speed of writing — in payments, an untraceable state jump is a compliance and money-reconciliation problem, not just a bug.
ResultEvery payment has a full, queryable audit trail of exactly how it reached its current state — the same guarantee PCI-DSS auditors and support teams actually ask for when a merchant disputes a transaction.

more design decisions
Redis fixed-window rate limiter, not sliding window (yet). A single INCR + EXPIRE per API key is O(1) and cheap enough to run on every request. It allows short bursts right at window boundaries — a known trade-off of fixed windows — which is acceptable for a v1; a sliding-window variant is on the roadmap once burst abuse actually shows up in traffic.
Card data never touches the database in plaintext. Vault module encrypts each PAN with a per-card Data Encryption Key (DEK), which is itself encrypted by a master key (envelope encryption) before storage — and the raw PAN is zero-filled from the JVM heap right after use. Only a tok_-prefixed token ever leaves the Vault module.
Cache-aside for API key lookups, not write-through. Every authenticated request needs to resolve an API key, so a DB hit per request doesn't scale. Redis holds a 5-minute TTL cache; on rotation or deletion the entry is explicitly evicted rather than waiting for expiry, so a revoked key can't be used from a stale cache.
a real challenge
Early on, merchant identity was threaded manually through every controller → service → repository call — easy to forget in a new endpoint and easy to get wrong. Fixed it with a @RequestScope-scoped MerchantContext bean populated once by whichever filter authenticates the request (JWT or API key), then injected anywhere downstream. It also feeds a custom AuditorAware implementation, so JPA's createdBy/updatedBy audit columns are populated automatically from keyId → merchantId → SYSTEM with zero boilerplate per entity.

LLM-Powered Full-Stack Application Generator
 
🚧 In Development

An AI-native platform that converts natural language prompts into fully working, deployable full-stack applications. Users chat with an LLM inside a Project workspace — the assistant generates and edits real code files stored in MinIO object storage, deployed live to isolated Kubernetes pods with shareable preview URLs. Billing gated via Stripe subscription plans.

→Multi-tenant workspace — User → Project → ChatSession → ChatMessage (USER/ASSISTANT/SYSTEM/TOOL roles) with complete message history
→MinIO object storage — generated code stored as objects (not in DB), referenced by object keys with path-based file tree API
→Live Preview Engine — per-project Kubernetes namespace + pod, PreviewStatus (CREATING/RUNNING/FAILED/TERMINATED), shareable URL
→Stripe billing — Plan tiers (project/token/preview limits), Subscriptions, checkout session + customer portal APIs, webhook handling
→Usage metering — UsageLog per action (tokens, duration, model, prompt metadata), plan-gated rate limiting per user
→RBAC collaboration — ProjectMember many-to-many with ProjectRole (OWNER/EDITOR/VIEWER), invite + role update + remove APIs
